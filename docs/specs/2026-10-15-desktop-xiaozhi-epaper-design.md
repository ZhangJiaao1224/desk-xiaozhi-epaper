## 1. 目标与非目标

目标：一块桌面设备能做到这几件事，做完能停下来玩几天。

1. 喊"小智小智"能对话（语音链路走 xiaozhi.me 官方云，简单对话即可）。
2. 墨水屏常驻显示时间 / 日期 / 星期 / 当天首次对时时刻 / 下次提醒时刻 / 喝水进度条。
3. 从开机起算每 45 分钟一轮本地语音提醒，提醒后用按键或语音记一杯。
4. 按键可以随时报时，报时同样走本地语音。
5. 杯数掉电不丢，跨天自动清零。

非目标：不做产品、不发版、不上 Home Assistant、不跑本地大模型、不在 ESP32 上跑视觉、
不做多版式切换、不引入 RTC 芯片、不依赖云端 TTS 播报。

## 3. 为什么必须自编译固件

上游预编译的 `merged-binary.bin` 把板级配置和显示驱动一起编进了二进制，官方变体里
不存在"本板 + 4.2 寸 SSD1683"的组合。所以：

- 刷预编译固件只能验证板子和语音链路，一旦要接墨水屏就必须自编译，那一次刷机基本白做。
- 自编译时**必须新建独立板型标识**，不能覆盖官方板型。否则 OTA 会把这个设备当成官方板型，
  用官方固件把它覆盖回去。

结论：直接走自编译路线，跳过"先刷官方固件"这一步。板子好坏可以在自编译固件上验证。

## 4. 架构

### 4.1 硬件链路

```
ESP32-S3-WROOM-1-N16R8（核心板 YB-MEV06-V1.0）
  ├─ ES8311 codec + MEMS 麦克风 + NS4150 功放
  │     I2S: MCLK=GPIO15 SCLK=GPIO16 ASDOUT=GPIO17 LRCK=GPIO18 DSDIN=GPIO8
  │     I2C: SDA=GPIO41 SCL=GPIO42（与 OLED 共线），PA 使能 Voice_EN=GPIO7
  ├─ SSD1306 128x32 OLED               (I2C 0x3C，H3 排针)
  ├─ 4.2" 墨水屏 SSD1683 400x300       (SPI，引脚见 hardware/引脚记录表.md)
  ├─ BOOT 按键 GPIO0 / WS2812 GPIO48   (配网 / 打断对话、状态灯)
  └─ WiFi 2.4G
        │  WSS
        ▼
  xiaozhi.me 官方服务端  ──HTTP──▶  DeepSeek / 通义千问
```

引脚的字面值一律从 `hardware/引脚记录表.md` 取，本文只写拓扑，两者冲突时以引脚记录表为准。

### 4.2 软件分层

在 `xiaozhi-esp32` 源码树上新增三块内容，其余官方代码不动。

```
main/boards/<我们的板型>/
    config.h                板级引脚与参数（照 hardware/引脚记录表.md 填）
    config.json             板型上报标识（必须唯一，防 OTA 覆盖）
    <board>.cc              板级初始化：I2C / SPI / 显示 / 按键 / codec

main/display/epd_ssd1683_420/
    epd_ssd1683_420.{h,cc}  纯 SSD1683 时序驱动，不依赖 LVGL
    epd_display_lvgl.{h,cc} 把驱动包成小智的 Display 接口 + 刷新节流
```

驱动拆成两层是为了让 `epd_ssd1683_420` 能脱离小智单独测试——到货当天先用一个极小的
IDF 工程点亮屏幕，确认接线和刷新参数，再编进小智固件。两层复用同一份驱动源文件，
不做复制粘贴。

### 4.3 显示定位：双屏

板子上有一块板载 OLED 小屏，用它做小智的**主显示**，墨水屏单独做**日历 / 喝水看板**。

| 屏幕 | 角色 | 刷新节奏 | 驱动来源 |
|---|---|---|---|
| 板载 SSD1306 128x32 OLED（I2C 0x3C） | 小智主显示：对话状态、表情、音量、配网提示 | 实时，跟随对话 | 上游现成的 OLED 显示类，不自己写 |
| 4.2" 墨水屏（SPI，SSD1683） | 日历页：时间 / 日期 / 星期 / 喝水杯数 | 每分钟一次，加状态变化时 | 本项目自己写 |

这样分工的好处很直接：小智的表情和状态变化走 OLED，是毫秒级的，体验正常；
墨水屏一分钟才动一次，0.42s 的局刷完全够用，不需要为了追上动画去做丢帧或冻结刷屏。

代价是两件事要解决：

1. **墨水屏的内容怎么画**。两个做法：把墨水屏也注册成第二个 LVGL display，用一个只放
   日历控件的独立 screen，内容不变 LVGL 就不 flush，做到每分钟只刷一次；或者干脆不用 LVGL，
   直接往 1bpp 帧缓冲里画点阵字。前者能复用项目自带的字体和图标资源，后者不碰 LVGL 多屏的坑
   但要自备字库（中文字形）。**倾向前者**，留待写实现计划时先验证。
2. **字体大小的取舍**。查过了，结论是：字体在构建期由 `--builtin_text_font` 单选，
   但打包成 assets 分区、运行时由 `Assets` 加载，并且 `Display::SetTextFont()` 和
   `LvglTheme` 是按 display 走的，所以"两块屏各挂一个字号"在机制上可行，
   只是要改 `scripts/build_default_assets.py` 和 `main/CMakeLists.txt` 让它多打包一个字体。
   第一版不这么做，日历页只用数字、星期数字和进度条，用一个中间字号即可；
   等真的嫌字小了再动 assets 生成脚本。

### 4.4 版式与交互规则（2026-10-16 定稿）

**只做一版版式**，400x300、纯黑白 1-bit，从上到下分成这几块：

| 位置 | 内容 |
|---|---|
| 左上 | `10月16日 周五` |
| 右上 | 对时状态：已对时显示信号条 + 「已对时」，未对时显示「未对时」 |
| 中部 | 超大 `HH:MM`（未对时显示 `--:--`） |
| 分隔线下 | `今日喝水` + `6 / 8 杯` + 一条**连续**进度条（不分格） |
| footer 左 | 当天首次对时时刻，如 `开机 08:12`；跨天未重启时显示「未重启」 |
| footer 右 | `下次提醒 08:57`；未对时改显示距下次提醒的分钟数 |

杯数超过目标时进度条封顶，数字照实显示（如 `10 / 8 杯`）。
草图（临时产物，不入库）：`.codex/visualizations/2026/10/15/<session>/calendar-v2-2x.png`
与 `calendar-v2-nontp-2x.png`。

**按键组**：4 路独立轻触按键模块，内部上拉，按下为低电平。

| 键 | 功能 | GPIO | 排针 |
|---|---|---|---|
| 键 1 | 记一杯 | GPIO4 | H1-4 |
| 键 2 | 报时 | GPIO5 | H1-5 |
| 键 3 | 备用（先只打日志） | GPIO6 | H1-6 |
| 键 4 | 备用（先只打日志） | GPIO21 | H2-18 |
| 公共端 | GND | — | H1-22 |

**BOOT 键 GPIO0 不动**，保持上游用法：启动阶段进配网、正常运行打断对话。

**喝水规则**：

1. 从开机起算，每 45 分钟一轮，到点只播提醒、**不**自动加杯。
2. 键 1 每轮最多记一杯：本轮第一次按下生效，同一轮内重复按忽略（播一声短提示音），
   额度不累积到下一轮。
3. 语音「刚才我喝水了」不受轮次限制，两次提醒之间说几次加几次；
   实现方式是注册一个 MCP 工具让语音助手调用。
4. 进度条按 `min(杯数, 8)` 填充，杯数照实显示。
5. 跨天清零，判定规则见第 7 节。

**报时**：键 2 按下后本地拼语音播「现在 下午 2 点 26 分」，整点省略「分」。
数字 0~9 的中文音源上游已有，需补齐「现在 / 上午 / 下午 / 点 / 分」几个音，
所有音必须同一套音色，否则会像几个人接力说话。

**提醒与报时全部走本地音效**，不依赖云端 TTS（理由见第 2 节与第 7 节）。
若正好撞上对话，本地音会被上游清掉，不做特殊处理。

## 5. 墨水屏刷新策略

改成双屏之后，刷新压力小了很多：墨水屏只在日历内容变化时刷新。
按第 4.4 节的版式，日常只有两处会变——大钟每分钟变一次，进度条只在杯数变化时变，
两块都是小区域，走局刷。但 4.2 寸屏的局刷有两件事必须先讲清：一件是已经确认的坑，
一件还是推断。

1. **差分同步**：局刷不是"只擦那一小块"。新帧写 `0x24`，上一帧要同时写进 `0x26`，
   再发 `0x22`（局刷控制字）+ `0x20`（激活）触发。上游 2.9 寸实现只写 `0x24`、从不写 `0x26`
   （读 `epd_display.cc` 确认），所以这份驱动不能照抄它。
   注意：面板手册把 `0x26` 标成 "Write RAM (RED)"，那是在 B/W/Red 面板上的含义；
   本板是纯黑白面板，`0x26` 被当作上一帧缓冲用。这一条目前是**推断**，
   必须以到货当天"只改一小块、看变化是否正确、有无残影"的实测为准。
   若不成立，退路是改用 `0x32` 自写局刷 LUT（面板手册允许 MCU 写 227 字节波形）。
2. **定期全刷**：每小时插一次全刷清残影（局刷攒久了会留印子）。手册标称全刷要 3s 且有明显黑白闪烁，
   所以固定低频，不做成每次刷新都全刷。

另外两条保险措施，成本很低：

- **防抖**：日历页面内部对刷新做合并，避免一秒钟内连着改多个控件导致连刷多次。
- **按键不碰刷屏**：按键回调只投递一个事件给刷新任务，绝不在回调里同步刷屏；
   否则那 3 秒全刷会把音频链路一起拖住。
- **空闲期刷**：只在设备空闲（非 Listening / Speaking）时执行墨水屏刷新，避免刷屏和
  音频任务抢 SPI 总线的时间片。这条不是必需的，但实现成本很低。

如果实测发现"每秒刷一次"这种场景仍然会卡，退化方案是把墨水屏刷新降级到"内容真正变化才刷，
且最小间隔 5 秒"。

## 6. 4.2 寸驱动要点

以厂家面板手册为准，GxEPD2 只当交叉参考，不作为验收标准。

### 6.1 手册给的标准流程（手册 13.2 节原文照抄）

| 步骤 | 动作 |
|---|---|
| 上电 | 延时 10ms |
| 硬复位 | RES# 拉低 200us → 拉高 200us → 读 BUSY 直到为低 |
| 软复位 | `0x12` → 读 BUSY |
| 尺寸 | `0x01` ← `0x2B 0x01 0x00`（A[8:0]=0x12B=299，即 300 行 MUX） |
| 数据入口 | `0x11` ← `0x01` |
| RAM 窗口 | `0x44` ← `0x00 0x31`（X 起止）；`0x45` ← `0x2B 0x01 0x00 0x00`（Y 起止） |
| 边框 | `0x3C` ← `0x01` |
| 写图 | `0x4E`←`0x00`、`0x4F`←`0x2B 0x00`、`0x24`←黑白字节流 |
| 刷屏 | `0x20` → 读 BUSY |
| 休眠 | `0x10` ← `0x01` |

### 6.2 会用到的寄存器（手册第 7 节命令表）

| 命令 | 作用 | 关键点 |
|---|---|---|
| `0x01` | Driver output control | A[8:0]=299，即 300 行 |
| `0x11` | Data entry mode | 决定 X/Y 扫描方向，改方向要同步改字节序 |
| `0x12` | 软复位 | |
| `0x18` | 温度传感器控制 | `0x80` 用片内传感器，`0x48` 用外部 |
| `0x0C` | Booster soft start | 手册给了默认值 |
| `0x22` | Display Update Control 2 | 选"载入 LUT + 显示"的组合，可取 `0xC7/0xCF/0xF7/0xFF` 等 |
| `0x20` | 激活 | 触发一次实际刷屏 |
| `0x24` / `0x26` | 写 RAM 0x24 / 0x26 | 差分方案见第 5 节 |
| `0x30` / `0x31` | 写 / 载入 OTP 波形 | |
| `0x32` | 写 LUT | 227 字节，MCU 自定义波形时用 |
| `0x3C` | 边框波形 | |
| `0x44` / `0x45` / `0x4E` / `0x4F` | RAM 窗口与光标 | X 方向以 8 像素为单位 |

### 6.3 时间与容量常量

| 项 | 值 | 来源 |
|---|---|---|
| 上电 | 10 ms | 面板手册 13.2 |
| 复位低 / 高 | 各 200 us | 面板手册 13.2 |
| 全刷 | 3 s（25℃） | 面板手册 6.2 注 1、第 8 节 |
| 快刷 | 1.5 s 或 1 s | 面板手册 6.2 注 1 |
| 局刷 | 0.42 s | 面板手册 6.2 注 1 |
| 屏尺寸 | 400x300 | 面板手册第 1 节 |
| 单帧字节数 | `400*300/8 = 15000` | 推导 |

GxEPD2 的库常量（全刷 1.6s、局刷 0.6s）与上表不一致，只能当交叉参考；
验收一律以到货当天串口打时间戳的实测值为准。

### 6.4 还没定的三件事（到货当天用最小工程逐个验）

1. 局刷要不要写 `0x26` 做差分（见第 5 节）。
2. 快刷全屏要不要先写 `0x1A` 温度寄存器、再走 `0x22` 的快刷组合。
3. 局刷用不用 `0x21`，以及用哪个 `0x22` 组合值。手册的标准流程里没有 `0x21`，
   GxEPD2 用了，两边对不上，以实测为准。

### 6.5 帧缓冲尺寸

上游 `EpdDisplay` 的 `buffer_len` 由板级传入（2.9 寸板传 5000），这是按屏算的，
4.2 寸必须传 15000，多传少传都会越界或花屏。本项目因为重写驱动，改为常量派生，不手填。

## 7. 时间、存储与每日重置

### 7.1 时间来源：不是 SNTP

v2 里写的"走 SNTP 对时"是错的，2026-10-16 复核源码后纠正：
上游没有 SNTP，时间来自服务器配置接口。

- 启动阶段 `Application::ActivationTask()` 调 `Ota::CheckVersion()`（`main/ota.cc:87`），
  响应里的 `server_time.timestamp` 加上 `timezone_offset` 后由 `settimeofday()` 写进系统
  （`main/ota.cc:196~222`）。所以**每次上电联网成功后天然就有一次对时**。
- 运行期间上游不会重新对时，跑久了会漂。本项目自己起一个定时任务，每 N 小时重建一个
  `Ota` 对象、只调 `CheckVersion()` 取时间字段。注意三点：间隔进配置（默认 3 小时，
  实测漂移后再调）；不能复用旧对象（`HandleActivationDoneEvent()` 里已经 `ota_.reset()`）；
  不要重跑 `Application::CheckNewVersion()`，那个会把激活、固件升级、资源包检查整套走一遍。
- 判断"是否已对时"沿用上游判据：`localtime` 年份 < 2025 视为未设置
  （`main/display/lvgl_display/lvgl_display.cc:220`）。
- **时区坑**：上游是把时区偏移直接加进时间戳的，等于"把本地时间当成 UTC"存进系统，
  所以我们的代码**不得**再设 `TZ` 环境变量，否则会双倍偏移 8 小时。到货第一天在屏幕上能直接验出来。

板上没有 RTC 电池，不新增 RTC 芯片；断电后时间靠下次上电重新对时恢复。

### 7.2 每日重置规则

把"对时"抽象成一个事件，**上电那次和定时那次同等对待**，走同一个日切函数：

1. 对时成功 → 把本次的本地日期与 NVS 里记录的日期比较：不同天（或首次没有记录）
   就清零杯数、更新日期、把本次时刻记为"当天首次对时"；同一天则只更新，其他不动。
2. 已对过时的情况下，另有一个分钟级检查：本地日期一变就清零，并把当天起点记为 00:00。
   这条负责"23:50 上电、00:00 归零"这种没有对时事件的跨天场景。
3. 定时对时负责纠正漂移、准点清零交给第 2 条；两条共用同一套日切逻辑，语义一致。

### 7.3 NVS 存储

用上游现成的 `Settings` 类（`main/settings.{h,cc}`，NVS 分区 16KB）存三个值：
上次对时日期、当天首次对时时分、当天杯数。杯数每次变化立即写，
写入是毫秒级，拔电那一瞬间也不会丢。

### 7.4 未对时期间的行为

不判跨天、不清零杯数（避免一开机就看到 0）。屏幕显示「未对时」、大钟显示 `--:--`、
footer 右侧改显示距下次提醒的分钟数，因为这时候还说不出墙上时间。提醒倒计时独立于时间，
照常走。

## 8. 硬件待确认清单

1. 板型：ESP32-S3 全功能核心板 YB-MEV06-V1.0，模组 ESP32-S3-WROOM-1-N16R8。

## 10. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 厂家资料里混了旧款驱动 IC 的文档 | 照着错的手册写驱动，白烧一天 | 以面板手册为准；`UC8176.pdf` 明确标注为无关资料（见 AGENTS.md 已知的坑第 3 条） |
| 局刷差分方案是推断，未实机验证 | 局刷不生效或花屏 | 到货当天第 1 步就用最小工程验；备选是 `0x32` 自写局刷 LUT |
| `0x21` 用不用、`0x22` 取哪个值，手册与 GxEPD2 对不上 | 刷屏时机不对，出现残影或全屏闪 | 两组组合值都写成可配置项，实测选优 |
| 面板 OTP 波形版本差异 | 快刷/局刷波形可能不生效 | 保留慢刷全屏（3s）作为兜底；必要时用 `0x32` 写自己的 LUT |
| 墨水屏只有黑白两色 | 彩色表情无法在墨水屏上呈现 | 已确认单色版；表情走 OLED，墨水屏只画文字和进度条 |
| 墨水屏面板可能实际是黑白红三色版 | 红色平面未接，`0x26` 语义与设计假设不同 | 开箱拍面板丝印确认；若是三色版，`0x26` 要按红色平面处理，差分方案另算 |
| 两个 display 共用一套字体 | OLED（128x32）和墨水屏字号需求不同，可能只能二选一 | 先查能否分屏设字体；查不清就让墨水屏不用 LVGL、自己画字 |
| 墨水屏 SPI 与音频/OLED 抢总线时间 | 刷屏时音频可能卡顿 | 只在空闲状态刷墨水屏；SPI 独立主机 |
| 全刷 3s 且明显闪屏 | 定期全刷时会看到明显的黑白反相过程 | 全刷固定低频（累计 60 次局刷或 6 小时），可选放在夜间 |
| 新板型标识被 OTA 当作官方板 | 固件被覆盖回官方版本 | 板型标识必须唯一，控制台里关掉 OTA 自动升级 |
| 工程路径含中文 | `idf.py build` 的 cmake 直接崩溃（退出码 `0xC0000409`），编译进行不下去 | 2026-10-15 实测确认；项目路径固定用纯 ASCII，不许改回中文目录名 |
| 时间靠内部计时，跑久了会漂 | 大钟显示偏差；日切提前或延后 | 每 3 小时（可配置）重建 `Ota` 重新对时；再靠每天断电重启兜底；实测后再调间隔 |
| 上游把时区偏移直接加进时间戳 | 代码里若再设 `TZ` 会双倍偏移，时间整整差 8 小时 | 代码里不设 `TZ`；到货第一天在屏幕上验一次 |
| 报时靠拼接音效 | 语速和停顿可能不自然；音色不统一会很难听 | 所有音源同一套音色；先做短句，听感不行再换成整句预录 |
| 提醒是本地音效，撞上对话会被上游清掉 | 那一次提醒听不到 | 接受，不做特殊处理；屏幕上的「下次提醒」仍然准 |
| 按键接线长或模块质量差 | 抖动误触发、按了没反应 | 上游 `Button` 类自带消抖；线材控制在 20cm 内；到货先手动按一遍确认低电平 |
| 自定义 ogg 挤占 assets 分区 | 打包失败或空间不够 | assets 分区 8MB，风险低；打包脚本带 `--max_size` 校验，超了会直接报错 |

## 11. 已定案的取舍

以下几条 2026-10-16 已与用户逐条确认，不再是待评审项：

1. **单版式**：只做大钟为主那一版，不做版式切换，因此不需要切换键。
2. **连续进度条**：不分格，超量封顶、数字照实显示。
3. **提醒与报时走本地音效**：设备端没有主动触发云端 TTS 的通道（第 2 节），
   所以不指望小智开口报时；云端 `notify` 留作以后若后台支持的升级路径。
4. **按键用 4 路独立轻触模块**：键 1 记杯、键 2 报时、键 3/4 备用；BOOT 键保持上游用途不动。
5. **时间来源沿用上游服务器对时 + 本机定时重对**：不引入 SNTP，也不加 RTC 芯片。
6. **每轮按键限一杯、语音不限**：语音记杯走 MCP 工具，属于对话流程，天然不受轮次约束。
7. **双屏分工不变**：OLED 走实时对话界面，墨水屏只做日历看板。
8. 项目目录固定在 `C:\Users\lenovo\Desktop\desk-xiaozhi-epaper`，
   **路径保持纯 ASCII**（理由见第 10 节）。

仍然待定的一项：墨水屏的内容渲染走 LVGL 第二个 display，还是自己往帧缓冲画点阵字。
倾向 LVGL，但取决于第 4.3 节提到的分屏字体问题，留到写实现计划时先验。

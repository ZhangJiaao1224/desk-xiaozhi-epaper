适用硬件：ESP32-S3 全功能核心板 YB-MEV06-V1.0（模组 ESP32-S3-WROOM-1-N16R8）+ 微雪 **4.2inch e-Paper V2**（400x300 单色，驱动 IC SSD1683）

## 1. 目标与非目标

目标：一块桌面设备能做到三件事，做完能停下来玩几天。

1. 喊"小智小智"能对话（语音链路走 xiaozhi.me 官方云）。
2. 墨水屏常驻显示时间 / 日期 / 星期 / 喝水进度。
3. 到点播报喝水，语音说"我喝了一杯"能记杯数并刷新屏幕。

非目标：不做产品、不发版、不上 Home Assistant、不跑本地大模型、不在 ESP32 上跑视觉。

## 2. 已核实的关键事实

以下几条查过源码、厂家手册与厂家文档，不是推测；凡属推断的地方在表里直接标注。

| 事实 | 依据 |
|---|---|
| 上游要求 ESP-IDF >= 6.0.1，推荐 6.1，不支持 5.x | `xiaozhi-esp32` v2.5.2 `README_zh.md` |
| 上游预编译固件按板型编译，共 171 个变体 | 同上 |
| 上游已有 EPD 驱动，但只有 2.9 寸 128x296 一种实现，仅 `maza-ai` 两块板使用 | `main/display/epd_display/` |

| 面板型号是微雪 **4.2inch e-Paper V2**，400x300，1-bit 黑白，支持局部刷新 | 厂家资料 `4.2-inch-e-Paper-V2.pdf` 第 1 节、第 2 节 |

| 刷屏耗时：全刷 3s、快刷 1.5s 或 1s、局刷 0.42s（25℃） | 同上手册 6.2 节注 1、第 8 节 "Image update time at 25℃ = 3s" |
| 波形可存 OTP，也可由 MCU 用 `0x32` 写 227 字节 | 同上手册第 2 节、命令表 `0x32` 行 |
| 厂家资料里的 `UC8176.pdf` **不是**本面板的驱动 IC | 该手册命令集（`0x00` PSR / `0x04` PON / `0x10` DTM1 / `0x13` DTM2 / `0x90~0x92` 局刷）与面板手册完全对不上，属厂家夹带的旧款资料 |

| 板载 codec 是 ES8311（I2C `0x18`）、功放 NS4150（GPIO7 使能）、RGB 灯 WS2812（GPIO48） | 同上文档第 4.5、4.6 节 |
| 上游自带 `Es8311AudioCodec`，板级 codec 类不用自己写 | `main/audio/codecs/es8311_audio_codec.{h,cc}` 存在，多个官方板型在用 |
| 上游 `OledDisplay` 按 height 自动选版式，`height=32` 走现成的 `SetupUI_128x32()` | `main/display/oled_display.cc` 第 98~102 行 |

## 3. 为什么必须自编译固件

上游预编译的 `merged-binary.bin` 把板级配置和显示驱动一起编进了二进制，官方变体里
不存在"本板 + 4.2 寸 SSD1683"的组合。所以：

- 刷预编译固件只能验证板子和语音链路，一旦要接墨水屏就必须自编译，那一次刷机基本白做。
- 自编译时**必须新建独立板型标识**，不能覆盖官方板型。否则 OTA 会把这个设备当成官方板型，
  用官方固件把它覆盖回去。

结论：直接走自编译路线，跳过"先刷官方固件"这一步。板子好坏可以在自编译固件上验证。

## 4. 架构

### 4.1 硬件链路

```
ESP32-S3-WROOM-1-N16R8（核心板 YB-MEV06-V1.0）
  ├─ ES8311 codec + MEMS 麦克风 + NS4150 功放
  │     I2S: MCLK=GPIO15 SCLK=GPIO16 ASDOUT=GPIO17 LRCK=GPIO18 DSDIN=GPIO8
  │     I2C: SDA=GPIO41 SCL=GPIO42（与 OLED 共线），PA 使能 Voice_EN=GPIO7
  ├─ SSD1306 128x32 OLED               (I2C 0x3C，H3 排针)
  ├─ 4.2" 墨水屏 SSD1683 400x300       (SPI，引脚见 hardware/引脚记录表.md)
  ├─ BOOT 按键 GPIO0 / WS2812 GPIO48   (配网 / 打断对话、状态灯)
  └─ WiFi 2.4G
        │  WSS
        ▼
  xiaozhi.me 官方服务端  ──HTTP──▶  DeepSeek / 通义千问
```

引脚的字面值一律从 `hardware/引脚记录表.md` 取，本文只写拓扑，两者冲突时以引脚记录表为准。

### 4.2 软件分层

在 `xiaozhi-esp32` 源码树上新增三块内容，其余官方代码不动。

```
main/boards/<我们的板型>/
    config.h                板级引脚与参数（照 hardware/引脚记录表.md 填）
    config.json             板型上报标识（必须唯一，防 OTA 覆盖）
    <board>.cc              板级初始化：I2C / SPI / 显示 / 按键 / codec

main/display/epd_ssd1683_420/
    epd_ssd1683_420.{h,cc}  纯 SSD1683 时序驱动，不依赖 LVGL
    epd_display_lvgl.{h,cc} 把驱动包成小智的 Display 接口 + 刷新节流
```

驱动拆成两层是为了让 `epd_ssd1683_420` 能脱离小智单独测试——到货当天先用一个极小的
IDF 工程点亮屏幕，确认接线和刷新参数，再编进小智固件。两层复用同一份驱动源文件，
不做复制粘贴。

### 4.3 显示定位：双屏

板子上有一块板载 OLED 小屏，用它做小智的**主显示**，墨水屏单独做**日历 / 喝水看板**。

| 屏幕 | 角色 | 刷新节奏 | 驱动来源 |
|---|---|---|---|
| 板载 SSD1306 128x32 OLED（I2C 0x3C） | 小智主显示：对话状态、表情、音量、配网提示 | 实时，跟随对话 | 上游现成的 OLED 显示类，不自己写 |
| 4.2" 墨水屏（SPI，SSD1683） | 日历页：时间 / 日期 / 星期 / 喝水杯数 | 每分钟一次，加状态变化时 | 本项目自己写 |

这样分工的好处很直接：小智的表情和状态变化走 OLED，是毫秒级的，体验正常；
墨水屏一分钟才动一次，0.42s 的局刷完全够用，不需要为了追上动画去做丢帧或冻结刷屏。

代价是两件事要解决：

1. **墨水屏的内容怎么画**。两个做法：把墨水屏也注册成第二个 LVGL display，用一个只放
   日历控件的独立 screen，内容不变 LVGL 就不 flush，做到每分钟只刷一次；或者干脆不用 LVGL，
   直接往 1bpp 帧缓冲里画点阵字。前者能复用项目自带的字体和图标资源，后者不碰 LVGL 多屏的坑
   但要自备字库（中文字形）。**倾向前者**，留待写实现计划时先验证。
2. **字体大小的取舍**。查过了，结论是：字体在构建期由 `--builtin_text_font` 单选，
   但打包成 assets 分区、运行时由 `Assets` 加载，并且 `Display::SetTextFont()` 和
   `LvglTheme` 是按 display 走的，所以"两块屏各挂一个字号"在机制上可行，
   只是要改 `scripts/build_default_assets.py` 和 `main/CMakeLists.txt` 让它多打包一个字体。
   第一版不这么做，日历页只用数字、星期数字和进度条，用一个中间字号即可；
   等真的嫌字小了再动 assets 生成脚本。

## 5. 墨水屏刷新策略

改成双屏之后，刷新压力小了很多：墨水屏只在日历内容变化时刷新，典型是每分钟一次。
但 4.2 寸屏的局刷有两件事必须先讲清：一件是已经确认的坑，一件还是推断。

1. **差分同步**：局刷不是"只擦那一小块"。新帧写 `0x24`，上一帧要同时写进 `0x26`，
   再发 `0x22`（局刷控制字）+ `0x20`（激活）触发。上游 2.9 寸实现只写 `0x24`、从不写 `0x26`
   （读 `epd_display.cc` 确认），所以这份驱动不能照抄它。
   注意：面板手册把 `0x26` 标成 "Write RAM (RED)"，那是在 B/W/Red 面板上的含义；
   本板是纯黑白面板，`0x26` 被当作上一帧缓冲用。这一条目前是**推断**，
   必须以到货当天"只改一小块、看变化是否正确、有无残影"的实测为准。
   若不成立，退路是改用 `0x32` 自写局刷 LUT（面板手册允许 MCU 写 227 字节波形）。
2. **定期全刷**：累计 60 次局刷或满 6 小时，插一次全刷清残影。手册标称全刷要 3s 且有明显黑白闪烁，
   所以固定低频，不做成每次刷新都全刷。

另外两条保险措施，成本很低：

- **防抖**：日历页面内部对刷新做合并，避免一秒钟内连着改多个控件导致连刷多次。
- **空闲期刷**：只在设备空闲（非 Listening / Speaking）时执行墨水屏刷新，避免刷屏和
  音频任务抢 SPI 总线的时间片。这条不是必需的，但实现成本很低。

如果实测发现"每秒刷一次"这种场景仍然会卡，退化方案是把墨水屏刷新降级到"内容真正变化才刷，
且最小间隔 5 秒"。

## 6. 4.2 寸驱动要点

以厂家面板手册为准，GxEPD2 只当交叉参考，不作为验收标准。

### 6.1 手册给的标准流程（手册 13.2 节原文照抄）

| 步骤 | 动作 |
|---|---|
| 上电 | 延时 10ms |
| 硬复位 | RES# 拉低 200us → 拉高 200us → 读 BUSY 直到为低 |
| 软复位 | `0x12` → 读 BUSY |
| 尺寸 | `0x01` ← `0x2B 0x01 0x00`（A[8:0]=0x12B=299，即 300 行 MUX） |
| 数据入口 | `0x11` ← `0x01` |
| RAM 窗口 | `0x44` ← `0x00 0x31`（X 起止）；`0x45` ← `0x2B 0x01 0x00 0x00`（Y 起止） |
| 边框 | `0x3C` ← `0x01` |
| 写图 | `0x4E`←`0x00`、`0x4F`←`0x2B 0x00`、`0x24`←黑白字节流 |
| 刷屏 | `0x20` → 读 BUSY |
| 休眠 | `0x10` ← `0x01` |

### 6.2 会用到的寄存器（手册第 7 节命令表）

| 命令 | 作用 | 关键点 |
|---|---|---|
| `0x01` | Driver output control | A[8:0]=299，即 300 行 |
| `0x11` | Data entry mode | 决定 X/Y 扫描方向，改方向要同步改字节序 |
| `0x12` | 软复位 | |
| `0x18` | 温度传感器控制 | `0x80` 用片内传感器，`0x48` 用外部 |
| `0x0C` | Booster soft start | 手册给了默认值 |
| `0x22` | Display Update Control 2 | 选"载入 LUT + 显示"的组合，可取 `0xC7/0xCF/0xF7/0xFF` 等 |
| `0x20` | 激活 | 触发一次实际刷屏 |
| `0x24` / `0x26` | 写 RAM 0x24 / 0x26 | 差分方案见第 5 节 |
| `0x30` / `0x31` | 写 / 载入 OTP 波形 | |
| `0x32` | 写 LUT | 227 字节，MCU 自定义波形时用 |
| `0x3C` | 边框波形 | |
| `0x44` / `0x45` / `0x4E` / `0x4F` | RAM 窗口与光标 | X 方向以 8 像素为单位 |

### 6.3 时间与容量常量

| 项 | 值 | 来源 |
|---|---|---|
| 上电 | 10 ms | 面板手册 13.2 |
| 复位低 / 高 | 各 200 us | 面板手册 13.2 |
| 全刷 | 3 s（25℃） | 面板手册 6.2 注 1、第 8 节 |
| 快刷 | 1.5 s 或 1 s | 面板手册 6.2 注 1 |
| 局刷 | 0.42 s | 面板手册 6.2 注 1 |
| 屏尺寸 | 400x300 | 面板手册第 1 节 |
| 单帧字节数 | `400*300/8 = 15000` | 推导 |

GxEPD2 的库常量（全刷 1.6s、局刷 0.6s）与上表不一致，只能当交叉参考；
验收一律以到货当天串口打时间戳的实测值为准。

### 6.4 还没定的三件事（到货当天用最小工程逐个验）

1. 局刷要不要写 `0x26` 做差分（见第 5 节）。
2. 快刷全屏要不要先写 `0x1A` 温度寄存器、再走 `0x22` 的快刷组合。
3. 局刷用不用 `0x21`，以及用哪个 `0x22` 组合值。手册的标准流程里没有 `0x21`，
   GxEPD2 用了，两边对不上，以实测为准。

### 6.5 帧缓冲尺寸

上游 `EpdDisplay` 的 `buffer_len` 由板级传入（2.9 寸板传 5000），这是按屏算的，
4.2 寸必须传 15000，多传少传都会越界或花屏。本项目因为重写驱动，改为常量派生，不手填。

## 7. 时间来源

板上没有 RTC，走 SNTP 联网对时（WiFi 已经常连），服务器用 `ntp.aliyun.com`。
断网期间靠系统时间继续走字，重新联网后自动校正。不新增 RTC 芯片。

## 8. 硬件待确认清单

### 8.1 已确认（2026-10-15，来自厂家原理图与文档）

1. 板型：ESP32-S3 全功能核心板 YB-MEV06-V1.0，模组 ESP32-S3-WROOM-1-N16R8。
2. 音频：I2S 五根线 + I2C 两根线 + PA 使能脚，全部已从原理图读出。
3. codec：ES8311（I2C `0x18`）；功放 NS4150；另有板载 MEMS 麦克风。
4. 板载显示：SSD1306 **128x32** OLED，I2C `0x3C`，与 codec 共用总线。
5. Flash / PSRAM：16MB + 8MB Octal，对应 `N16R8`。
6. 墨水屏驱动 IC：SSD1683（手册明写）。面板为微雪 4.2inch e-Paper V2。

### 8.2 仍要确认（到货当天）

1. 墨水屏面板丝印上的具体型号后缀，确认是 `SSD1683` 而不是同系的其它编号。
2. 墨水屏驱动板上的 BS 跳线位置（必须选 4 线 SPI，`BS=L`）。
3. 板载 OLED 的即插排针 H3 是否已焊、4 根线序是否是 3V3 / SDA / SCL / GND。
4. 扬声器是不是随板附带的 2-pin PH 插头，阻抗是否匹配 NS4150。
5. USB-C 线是不是数据线（有些只能充电）。

记录表见 `hardware/引脚记录表.md`。

## 9. 分阶段计划

### Phase A：不依赖硬件的部分（现在做）

- A1 装 ESP-IDF 6.1。**已完成**
- A2 拉 `xiaozhi-esp32` v2.5.2 源码（当前最新正式 tag，`main` 上只有未发布的 2.5.3）。**已完成**
- A3 写 4.2 寸 SSD1683 驱动 + 一个极小的点亮工程。
- A4 先编译上游 `maza-ai` 板型，验证工具链能出固件、能打包成 `merged-binary.bin`。**已完成**
  （2026-10-15 编译通过，产出 8.54MB 的 `merged-binary.bin`）。
- A5 整理硬件待确认清单，发给卖家。**已完成**（第 8.1 节）。
- A6 填 `hardware/引脚记录表.md` 并选定墨水屏 SPI 引脚。**已完成**。

### Phase B：到货当天

- B1 确认板型与引脚，填 `config.h`。
- B2 用最小工程点亮墨水屏，验全刷 / 局刷 / 残影 / 实际耗时。
- B3 编自定义板固件，烧录，配网，绑 API Key，跑通第一次对话。
- B4 测刷新节流：对话时画面是否可接受。

验收：喊"小智小智"能对话；墨水屏显示时间且每分钟更新；对话时不被刷屏卡死。

### Phase C：联动（玩的部分）

- C1 日历页：时间 / 日期 / 星期 / 喝水进度，SNTP 对时。
- C2 到点播报喝水（本地 WAV，不依赖云端 TTS）。
- C3 语音记杯数："我喝了一杯" → 进度 +1 → 刷屏。

## 10. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 厂家资料里混了旧款驱动 IC 的文档 | 照着错的手册写驱动，白烧一天 | 以面板手册为准；`UC8176.pdf` 明确标注为无关资料（见 AGENTS.md 已知的坑第 3 条） |
| 局刷差分方案是推断，未实机验证 | 局刷不生效或花屏 | 到货当天第 1 步就用最小工程验；备选是 `0x32` 自写局刷 LUT |
| `0x21` 用不用、`0x22` 取哪个值，手册与 GxEPD2 对不上 | 刷屏时机不对，出现残影或全屏闪 | 两组组合值都写成可配置项，实测选优 |
| 面板 OTP 波形版本差异 | 快刷/局刷波形可能不生效 | 保留慢刷全屏（3s）作为兜底；必要时用 `0x32` 写自己的 LUT |
| 墨水屏只有黑白两色 | 彩色表情无法在墨水屏上呈现 | 已确认单色版；表情走 OLED，墨水屏只画文字和进度条 |
| 墨水屏面板可能实际是黑白红三色版 | 红色平面未接，`0x26` 语义与设计假设不同 | 开箱拍面板丝印确认；若是三色版，`0x26` 要按红色平面处理，差分方案另算 |
| 两个 display 共用一套字体 | OLED（128x32）和墨水屏字号需求不同，可能只能二选一 | 先查能否分屏设字体；查不清就让墨水屏不用 LVGL、自己画字 |
